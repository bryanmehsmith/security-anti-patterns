Module 1

Email vs. SFTP: who has a copy, and can you take it back?

"I emailed it to them" and "I put it on the SFTP" feel like the same action. They aren't always different in the way people assume, though: whether SFTP actually avoids the problem email has depends on who controls the server. There's more to the comparison too: how easily either one reaches the wrong person by accident, and what each protocol actually guarantees about encryption in transit. But once any copy exists, by any method, what happens to it next is the same problem either way.

Plain language: certainty and timing (it depends who owns the server)

Email is a store-and-forward system: the moment you hit send, the message is delivered to the recipient's mail server and inbox (infrastructure you don't administer) unconditionally. There is no step in between where you could stop that from happening. SFTP can genuinely avoid that problem, but only if you're the one administering the server: if it's yours (or your organization's), nothing is copied anywhere else until someone with valid credentials actually connects and downloads it, and you can revoke access at any point before that happens. If instead you're uploading to a server a third party hosts (a client's, a vendor's, a managed file-transfer platform), the moment you upload, a copy already exists on infrastructure you don't control, same as email's recipient mailbox, and you may not even be able to revoke it yourself. The advantage belongs to whoever administers the server, not to SFTP as a protocol.

Technical detail

SMTP relays a message hop-by-hop (sender's server → possibly intermediate relays → recipient's server), and each hop typically negotiates encryption opportunistically via STARTTLS: if the next hop doesn't support it, or under an active downgrade, the connection can fall back to plaintext (mitigations like MTA-STS help but aren't universal). Each relay also decrypts and re-encrypts, so every hop's administrator can, in principle, read the plaintext in transit. SFTP runs over SSH, which has no plaintext fallback: the whole transfer is one mutually authenticated, encrypted tunnel directly between client and server, with no intermediate relay ever seeing the content. That transport-level guarantee holds regardless of who administers the server; it's the "nothing is copied until someone downloads it" advantage above that depends on server ownership, not this one. It also assumes reasonably configured SSH (strong keys or MFA, not password-only auth); a badly configured SFTP server can still be worse in practice than a well-configured, modern mail setup.

Plain language: the human factor

There's a separate risk that has nothing to do with either protocol: sending it to the wrong person. Composing and addressing an email is one fast, autocomplete-assisted action (a similarly-named contact, a stale address-book entry, a reply-all), and misdirected email is consistently one of the most common real-world causes of accidental data exposure. Sharing over SFTP usually requires a separate, more deliberate step: creating an account or credential for a specific person, or generating a link for them. That doesn't make sending it to the wrong person impossible (access can still be misconfigured, or a credential shared with the wrong contact), but it removes the specific "autocomplete grabbed the wrong Sarah" failure mode that a To: field invites.

Technical detail

This is a workflow/UX risk, not a cryptographic one, and it's orthogonal to both axes above: it applies regardless of how strong the encryption is on either side, and no amount of transport security fixes an address typed to the wrong person.

Module 2

"Password-protected" isn't the same as "safe"

Putting a password on a zip or Office file feels like locking a door. Whether that lock actually holds depends on the password itself, which encryption scheme the file format uses, and how much hardware an attacker is willing to throw at it. Change any of those and "safe for years" can become "safe for seconds."

Plain language

A password-protected file isn't cracked by guessing it politely, one attempt at a time through the file's own dialog box; it's cracked by extracting the encrypted data and testing millions or billions of candidate passwords per second offline, with no lockouts and no rate limits. How long that takes depends on how many possible passwords there are (length and character variety) and how fast the attacker's hardware can test them against this specific file format.

Technical detail

Password entropy in bits is H = L × log2(N), where L is password length and N is the size of the character set used. The full search space is N^L candidates. An offline attacker's effective speed depends heavily on the file format's key-derivation scheme: legacy ZIP ("ZipCrypto") uses a fast, cryptographically weak stream cipher that GPUs tear through; modern AES-256 zips and Office 2013+ documents run the password through a deliberately slow key-derivation function (PBKDF2 for AES zips; a similar PBKDF2-like iterative SHA-512 hash chain for Office, often 100,000+ rounds), which is specifically designed to blunt hardware acceleration.

Module 3

One reused password, five compromised accounts

Password reuse turns a single breach at a site you barely think about into access across everything else you use the same password for.

When a breached site's password database leaks, attackers don't just try that password on that site; they run it (and every other leaked password) against every other major site the same email address might be registered on. This is called credential stuffing, and it's almost entirely automated.

Technical detail

Credential-stuffing tools take breach dumps of (email, password) pairs and replay them at scale against banking, email, retail, and social login endpoints, relying on the well-documented fact that a large share of users reuse passwords across sites. Multi-factor authentication (MFA) blocks stuffing even when the password is correct, because the attacker still lacks the second factor, which is why MFA coverage matters as much as password uniqueness.

Module 5

Data at rest: protected until it isn't

A password or lock screen only protects data while the device is on and locked. What happens the moment that assumption breaks (a lost laptop, a misconfigured bucket, an unlocked phone) depends entirely on what's underneath.
