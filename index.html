Module 1

Email vs. SFTP: who has a copy, and can you take it back?

"I emailed it to them" and "I put it on the SFTP" feel like the same action. They aren't. One creates a growing, uncontrollable number of copies the moment you hit send; the other keeps the file in one place you can cut off instantly.

Plain language

When you email a file, a copy lands in your Sent folder, a copy lands in the recipient's inbox, and copies pass through mail servers and backup systems on both ends — all before anyone forwards or downloads anything. Every one of those copies is now out of your hands. When you share a file over SFTP (or any managed transfer with access control), there is exactly one copy, sitting in one place, and you can revoke access to it at any moment.

Technical detail

Email traverses SMTP relays, is retained in journaling/archiving systems for compliance, and is backed up on both the sender's and recipient's mail infrastructure — typically for 30–90+ days, often indefinitely for legal-hold or backup-retention reasons. Transport is usually TLS-encrypted hop-to-hop (opportunistic STARTTLS), not end-to-end, so each relay can read the plaintext in transit. Attachment scanning/DLP gateways may also make and retain their own copies. SFTP (or an access-controlled managed-transfer service) keeps one file at a rest location behind authentication, encrypts the transfer channel end-to-end for that hop, and access is a database row you can delete — there's no equivalent of a "Sent folder" copy that outlives the transfer.

      Module 2

      "Password-protected" isn't the same as "safe"

      Putting a password on a zip or Office file feels like locking a door. Whether that lock actually holds depends on the password itself, which encryption scheme the file format uses, and how much hardware an attacker is willing to throw at it. Change any of those and "safe for years" can become "safe for seconds."

      Plain language

      A password-protected file isn't cracked by guessing it politely, one attempt at a time through the file's own dialog box — it's cracked by extracting the encrypted data and testing millions or billions of candidate passwords per second offline, with no lockouts and no rate limits. How long that takes depends on how many possible passwords there are (length and character variety) and how fast the attacker's hardware can test them against this specific file format.

      Technical detail

      Password entropy in bits is H = L × log2(N), where L is password length and N is the size of the character set used. The full search space is N^L candidates. An offline attacker's effective speed depends heavily on the file format's key-derivation scheme: legacy ZIP ("ZipCrypto") uses a fast, cryptographically weak stream cipher that GPUs tear through; modern AES-256 zips and Office 2013+ documents run the password through a deliberately slow key-derivation function (PBKDF2, often 100,000+ iterations for Office), which is specifically designed to blunt hardware acceleration.

      Module 3

      One reused password, five compromised accounts

      Password reuse turns a single breach at a site you barely think about into access across everything else you use the same password for.

      When a breached site's password database leaks, attackers don't just try that password on that site — they run it (and every other leaked password) against every other major site the same email address might be registered on. This is called credential stuffing, and it's almost entirely automated.

      Technical detail

      Credential-stuffing tools take breach dumps of (email, password) pairs and replay them at scale against banking, email, retail, and social login endpoints, relying on the well-documented fact that a large share of users reuse passwords across sites. Multi-factor authentication (MFA) blocks stuffing even when the password is correct, because the attacker still lacks the second factor — which is why MFA coverage matters as much as password uniqueness.

      Module 5

      Data at rest: protected until it isn't

      A password or lock screen only protects data while the device is on and locked. What happens the moment that assumption breaks — a lost laptop, a misconfigured bucket, an unlocked phone — depends entirely on what's underneath.
